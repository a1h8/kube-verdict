# Reasoning-path tests — grade every step of the diagnosis, not only the answer

> Spec 2026-10-17, not implemented. Why: the veracity replay grades only the final
> answer, so a right answer reached by luck and a wrong answer caused by one step look
> the same. These tests say **at which step** each case fails. Steps 1–5 are
> deterministic (no LLM) and run in CI; step 6 runs in the veracity replay; step 7
> (fix applicable) is deterministic and runs in CI.

## The steps, and where each is observable

| # | Step | Observed on | Question |
|---|---|---|---|
| 1 | Seeds | `dedup.bfs.find_unhealthy(graph)` | Are the faulty workloads picked as the starting point, and only them? |
| 2 | Path to the cause | `dedup.bfs.expand_incident_context` | From the seeds, is the object where the cause lives reached? |
| 3 | Evidence in context | `ContextBuilder.build()` sections | Does the discriminating evidence reach the prompt, in the section it belongs to? |
| 4 | Hypothesis ranking | `RemediationEngine.score(graph)` | Is the right hypothesis in the top 3, on the right object, above the decoys? |
| 5 | What the model is told | `RecordingLLM.analyze_prompts` (`HYPOTHESIS TO INVESTIGATE`) | Is a wrong hypothesis imposed on the model? |
| 6 | Conclusion | `report_dict.root_cause` + grading | Does the answer name the cause concepts, and cite the evidence rather than the symptom? |
| 7 | Fix applicable | proposed commands vs `ResourceQuota` (hard − used) and `LimitRange` bounds | Would the fix be admitted for every pod it creates, including the rollout surge? |

## Per-case declaration — `expect.json["path"]`

Written from the scenario, before running the tests, like the cause concepts.

```json
"path": {
  "seeds": ["Pod/production/api-5f7c9d8b6-mn4x8"],
  "cause_location": "Deployment/production/api",
  "evidence": [{"section": "drift", "marker": "resources_limits_memory"}],
  "rule": {"id": "helm_drift", "affected": "Deployment/production/api"},
  "decoy_rules": []
}
```
(h003: the OOMKilled pod is the seed; the cause is the Deployment's memory limit,
deployed 128Mi against 512Mi declared.)


| Field | Test | Fails when |
|---|---|---|
| `seeds` | step 1 | a declared seed is missing, or a healthy object is a seed |
| `cause_location` | step 2 | the object is not in the expanded context (a hop is missing in the graph) |
| `evidence` | step 3 | a marker is absent, or present only in another section |
| `rule` | step 4 | the rule is not in the top 3, or names another object; `null` when no rule is expected (the cause is only in telemetry) |
| `decoy_rules` | step 4 | a decoy rule ranks above `rule` |
| — | step 5 | the injected hypothesis is a decoy rule's |
| — | step 6 | the cause concepts fail (`docs/case-audit-001.md` § Correction 1) |

## Report

`tests/veracity/PATH.md`, regenerated by the test run: one row per case, one column per
step, PASS / FAIL / n.a., so the first failing step of each case is visible at a glance.
A case is "diagnosable" only if steps 1–5 pass: a model cannot be blamed for a step-6
failure when an earlier step already lost the cause.

## Rules

- A missing rule is a finding, not a test to skip: `rule: null` is allowed only when the
  scenario says the cause is visible in telemetry alone (h013–h015), and is then checked
  in step 3.
- The tests run on the cases as corrected by `docs/case-audit-001.md`; a case under
  correction is marked `xfail` with the correction it waits for, never deleted.
- No step is graded on the LLM's wording except step 6.
