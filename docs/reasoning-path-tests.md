# Reasoning-path tests — grade every step of the diagnosis, not only the answer

> Spec 2026-10-17, not implemented. Why: the veracity replay grades only the final
> answer, so a right answer reached by luck and a wrong answer caused by one step look
> the same. These tests say **at which step** each case fails. Steps 1–5 are
> deterministic (no LLM) and run in CI; step 6 runs in the veracity replay; step 7
> (fix applicable) is deterministic and runs in CI.

## The steps, and where each is observable

| # | Step | Observed on | Question |
|---|---|---|---|
| 1 | Seeds | `dedup.bfs.find_unhealthy(graph)` | Are the faulty workloads picked as the starting point, and only them? |
| 2 | Path to the cause | `dedup.bfs.expand_incident_context` | From the seeds, is the object where the cause lives reached? |
| 3 | Evidence in context | `ContextBuilder.build()` sections | Does the discriminating evidence reach the prompt, in the section it belongs to? |
| 4 | Hypothesis ranking | `RemediationEngine.score(graph)` | Is the right hypothesis in the top 3, on the right object, above the decoys? |
| 5 | What the model is told | `RecordingLLM.analyze_prompts` (`HYPOTHESIS TO INVESTIGATE`) | Is a wrong hypothesis imposed on the model? |
| 6 | Conclusion | `report_dict.root_cause` + grading | Does the answer name the cause concepts, and cite the evidence rather than the symptom? |
| 7 | Fix applicable | proposed commands vs `ResourceQuota` (hard − used) and `LimitRange` bounds | Would the fix be admitted for every pod it creates, including the rollout surge? |

## Per-case declaration — `expect.json["reasoning_path"]`

Written from the scenario, before running the tests, like the cause concepts.

```json
"reasoning_path": {
  "seeds": ["Pod/production/api-5f7c9d8b6-mn4x8"],
  "cause_location": "Deployment/production/api",
  "evidence": [{"section": "drift", "marker": "resources_limits_memory"}],
  "rule": {"id": "helm_drift", "affected": "Deployment/production/api"},
  "decoy_rules": []
}
```
(h003: the OOMKilled pod is the seed; the cause is the Deployment's memory limit,
deployed 128Mi against 512Mi declared.)


| Field | Test | Fails when |
|---|---|---|
| `seeds` | step 1 | a declared seed is missing, or a healthy object is a seed |
| `cause_location` | step 2 | the object is not in the expanded context (a hop is missing in the graph) |
| `evidence` | step 3 | a marker is absent, or present only in another section |
| `rule` | step 4 | the rule is not in the top 3, or names another object; `null` when no rule is expected (the cause is only in telemetry) |
| `decoy_rules` | step 4 | a decoy rule ranks above `rule` |
| — | step 5 | the injected hypothesis is a decoy rule's |
| — | step 6 | the cause concepts fail (`docs/case-audit-001.md` § Correction 1) |

## Report

`tests/veracity/PATH.md`, regenerated by the test run: one row per case, one column per
step, PASS / FAIL / n.a., so the first failing step of each case is visible at a glance.
A case is "diagnosable" only if steps 1–5 pass: a model cannot be blamed for a step-6
failure when an earlier step already lost the cause.

## Rules

- A missing rule is a finding, not a test to skip: `rule: null` is allowed only when the
  scenario says the cause is visible in telemetry alone (h013–h015), and is then checked
  in step 3.
- The tests run on the cases as corrected by `docs/case-audit-001.md`; a case under
  correction is marked `xfail` with the correction it waits for, never deleted.
- No step is graded on the LLM's wording except step 6.

## Findings (2026-10-17, first run on the 9 kept cases)

Three failures of the first run were errors in the declarations, not in the code, and were
corrected before anything else: the drift marker is written `resources.limits.memory` in the
prompt (not the annotation key), and the drift is reported on `HelmRelease/production/api`,
the right release under another kind. After that, 5 cases pass steps 1–4 (h001, h003, h004,
h009, h024); the failures below are strict xfails in `tests/unit/test_reasoning_path.py`.

| Id | Case / step | Finding |
|---|---|---|
| P1 | h016 seeds | Running-but-NotReady pods are not seeds (`dedup/bfs.py`: phase or restarts only) — **fixed 2026-10-17** |
| P2 | h022 seeds | any past restart makes a pod a seed, however old: the healthy cluster has an "unhealthy" pod — **fixed 2026-10-17** |
| P3 | h007 seeds | the fixture has no Deployment, HPA or metrics-server |
| P4 | h007, h008, h016 rule | no rule for HPA metrics, init-container failure, connection exhaustion |
| P5 | h016 rule | `helm_drift` on the decoy catalog-api ranks first — **fixed 2026-10-18**: the drift was false, made by linking every object of the namespace to the case's release (`docs/fix-plan-001.md`, H26); `drift.config` is now forbidden for h016 |
| P6 | h008 rule | `pending_unschedulable` fires for an init container that exits non-zero |

**The rule step grades the structured diagnoses (2026-10-19, `docs/structured-in-product.md`
rule 7).** The old `RemediationEngine` is no longer the product's engine, so the step ranks
`diagnose()`'s diagnoses (rule, cause location), top 3. Each case's expected rule was rewritten
from its declared `cause` (the absent object, the object, the outside dependency), never from
the output: h001 / h004 / h024 `dependency.missing` on the absent object; h003 / h024
`oom.memory_drift` on the Deployment; h007 `hpa.metrics`; h008 `init.failed`; h009
`config.drift` on the release; the decoys map family to family (`crashloop_db` →
`container.crash`, `pending_unschedulable` → `scheduling`, `helm_drift` on catalog-api →
`config.drift` there). **P4 (h007, h008) and P6 are fixed** by the structured families; P4 stays
for h016 (no connection-exhaustion family). Found: on h003 the generic `config.drift` of the
memory *request* (0.65) ranks above `oom.memory_drift` (0.5) — the specific rule is in the top 3,
the ordering is a finding (P7), not changed here.

**Fix of P1 / P2 (2026-10-17).** A pod is a seed when it is not Running or a container is
not ready; a past restart alone is not. A not-ready pod is skipped only when it starts
cleanly (every container running, never restarted) in a rollout Kubernetes reports as
progressing while the Deployment stays available — the negative case h026. A first version
skipped any not-ready pod of a progressing rollout; h003 caught it: `Progressing=True`
stays set until `progressDeadlineSeconds` even when the new pods crash, so that version hid
a broken rollout. Deployment conditions are now collected live and from fixtures alike.
Tests: `tests/unit/test_seed_selection.py`; after the fix 7 of 10 cases pass steps 1–4.

"Evidence PASS" means the marker is in the prompt **sent**; the model read only ~17 % of it
until the context window is fixed (`docs/case-audit-001.md` F8).
